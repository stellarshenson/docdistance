## Entries

- **X1 - block tags that are read as inline** (`src/docdistance/encoders.py`, `_HTML_PARAGRAPHS` and the dropped set): `<header>Site</header><nav>Home</nav><main>Body text</main><footer>Foot</footer>` converts to `SiteHomeBody textFoot`. Add to the paragraph tags: `header`, `footer`, `main`, `nav`, `aside`, `figure`, `details`, `summary`, `address`, `form`. Add to the tags dropped with their content: `noscript`, `svg`, and `title` wherever it stands (a document may omit the optional `head` tag). Tests: the verifier's three strings and one test per added tag
- **X2 - an ordered list** (`html_to_markdown`): an `li` inside an `ol` is written `- item`, so against the markdown line `1. item` a detail file reads `identical: false` at cost 0. Write the items of an `ol` as `1. `, `2. `, ... counted from 1 inside each `ol` (nested lists keep the two-space indentation per level; a nested `ol` counts from 1 again; the `start` attribute is not read). `ul` items stay `- `. Extend the twin fixture with an ordered list and assert that the reported lines of the two twins are equal. This corrects the table of my brief
- **X3 - markdown that holds HTML in a fence** (`detect_format`): a markdown document with one fenced code block that holds a page skeleton reads `html`. Lines inside a fenced block (between two lines that start with three backticks or three tildes) do not count for rule 1: not as document markers and not as tag lines; they also do not count as non-blank lines of the share. The fence rule of the markdown signals is unchanged. Tests: the verifier's two fenced cases read `markdown`; an HTML document whose `pre` holds a line of three backticks still reads `html` through its document marker outside the fence. State as a limit in the docstring and in `docs/cli-reference.md` and `docs/api-reference.md`: a markdown document in which at least half of the non-blank lines outside fences start with a tag reads `html`
- **X4 - text in front of the document marker** (`detect_format`, `html_to_markdown`): `﻿<!DOCTYPE html>...`, `<?xml version='1.0'?><!DOCTYPE html>...` and `<!-- comment --><!DOCTYPE html>...` on one line read `plain`, and an HTML file with a byte order mark gains a statement that holds U+FEFF only. For rule 1 a document marker also counts when only a byte order mark, an XML declaration, comments and whitespace stand between the start of the text and the marker. `html_to_markdown` removes U+FEFF from its output. The `plain` and `markdown` readers keep their reading of a byte order mark: that is 1.1.5 behaviour and not part of this entry. Tests: the three strings read `html`; the byte order mark case returns no statement that holds U+FEFF
- **X5 - three behaviours without a test that can fail** (verifier's mutations): add one test each for (a) `auto` detects on the file content before the title lines are removed (`pipeline._read_as`), (b) a line that starts with `<br/>` counts as a tag line, (c) a line that starts with a custom element such as `<my-card>` counts as a tag line. Each test fails on the verifier's mutation; say how you confirmed it
- **X6 - the advice of the marker warning under `auto`** (`_warn_marker_statements`): when the requested value is `auto`, the reader that ran is already the result of the detection, so the advice `--input-format auto` cannot change anything. Under `auto` the advice names `--input-format markdown` / `--markdown` and `--min-words`; under the default reader it stays as it is. This corrects line 41 of my brief; the test that pins the old wording under `auto` changes with it
- **X7 - a false path warning** (`_looks_like_path` in `src/docdistance/pipeline.py`): a raw HTML text on one line under 256 characters logs 'looks like a file path but no such file exists', because every closing tag holds `/`. A text that holds `<` is not read as a path. Test: the verifier's one-line fragment logs no such warning under `input_format="auto"`; a missing path such as `docs/missing.md` still logs it
- **X8 - quadratic time of the separator-row rule** (`_MARKDOWN_LINE_RE` in `encoders.py`): `detect_format("prose\n|" + "-" * 16000 + "x\n")` takes 1.3 s and grows by a factor of 4 per doubling. Decide a separator row without backtracking, with the rule `split_markdown` already uses for it (every cell holds only `-`, `:` and spaces, and at least one `-`). Test: that input with 200000 dashes returns in under 1 second, and the existing separator-row cases stay green
- **X9 - the check script of the batch memos** (`reports/E13-campaign/checks/batch-memos/measure.py`, the call `_memo_key(doc, False, 0, False)`): the second parameter is now the requested input format; pass `"plain"`
- **X10 - the command line step of the `DEF-DEPS-17` error** (`tests/test_cli.py`): the first package's verifier found that 'docdistance init exits 1 and names the tokenizer' rests on one manual run. Add a test with a stub: `bootstrap.init` raises `ModelsNotInstalled` with a message that names `facebookAI/xlm-roberta-base`; the command exits with the code the other commands use for that error and prints the message
